# Mucho AI Backend Implementation Plan

> **Update, 2026-06-10:** The decision in this document to defer state merging
> has been superseded by `iterative_workflow.md`. The implemented backend now
> supports a stateless Unity/AI action loop followed by semantic state
> placeholder merging. This document remains the original architecture guide.

This document is a Codex-ready implementation brief for a first Mucho AI backend. It focuses on automating the boring manual step where a designer inspects the Mucho timeline, moves keyframes, and adds effects to objects after recording/miming an XR interaction.

The scope is deliberately narrow: **generate timeline effect proposals from a recorded Mucho example plus the designer's spoken description**. State generation and state merging are acknowledged but deferred.

---

## 1. Context

Mucho is a no-coding immersive XR prototyping tool for interactive multimodal XR experiences. In recording mode, designers demonstrate input examples that populate a timeline representation with events. In playback mode, designers create a video-like prototype by adding system actions/effects at the relevant timeframes. In live mode, Mucho creates a state machine to test the interactive experience at runtime.

The current Mucho workflow is approximately:

1. The designer/player adds assets to the scene.
2. The designer records themselves acting out the interaction.
3. Mucho runs a first simulation, checking for hand gestures, collisions, and other observable events.
4. The designer manually moves through the timeline and selects useful keyframes.
5. The designer manually adds effects to objects, for example:
   - the ball should follow the hand;
   - the ball should stop following the hand;
   - an impulse should be applied to the ball;
   - the text `Hit` should appear;
   - the trash bin should change color;
   - an object should show/hide.
6. The designer generates states. By default, there may be too many states, because each delimiting sequence can become a start/end state. The designer may later merge states.

The target of this backend is **Step 4 and Step 5 above**, not the state-merging part yet.

---

## 2. Main Goal

The backend should receive:

- the audio recording of the designer talking while/after acting;
- the scene manifest from Unity;
- the frame-based recording metadata;
- the simulation trace generated by Mucho/Unity;
- the valid effect catalog supported by Unity;
- optionally, the existing timeline and default effects.

The backend should return a JSON object that Unity can parse into **timeline effect proposals**.

In plain terms:

> Given what the designer said and what Mucho observed in the recording, propose which effects should be added to which objects at which frames.

The output should be a **patch**, not a full replacement of the timeline. Unity should decide whether to apply it immediately or preview it to the user.

---

## 3. Non-Goals for Version 1

The backend should not try to solve everything at once.

For v1, do **not** implement:

- automatic state-machine generation;
- automatic state merging;
- full video understanding;
- continuous live voice streaming;
- direct Unity project mutation from the backend;
- open-ended natural-language effect creation outside the supported Unity effect catalog;
- hallucinated objects, effects, gestures, or frames.

State generation can come later. The backend should still structure its output in a way that will be useful for future state generation.

---

## 4. Critical Design Position

The backend should not rely on audio alone.

Audio such as `now the ball follows my hand, then when I open my hand it jumps, and when it hits the wall it turns red` is underspecified. It does not reliably contain exact object IDs, exact frames, collision partners, hand identity, or effect parameters.

Therefore, Unity should send structured context. The AI should align the speech with this context.

The most important idea is:

> Let Unity detect low-level facts. Let the AI interpret designer intent.

Unity/Mucho should provide:

- frame rate;
- duration in frames;
- object IDs and human-readable names;
- valid effects per object;
- gesture events;
- collision events;
- proximity events, if available;
- gaze events, if available;
- existing timeline effects;
- candidate keyframes extracted from simulation.

The AI should infer:

- which spoken instruction refers to which event;
- which object is the target of the effect;
- which frame/keyframe is the best anchor;
- which effect type and parameters should be used;
- whether confidence is high enough or the result needs user review.

---

## 5. Recommended v1 Architecture

Use a small backend service with this pipeline:

```text
Unity
  |
  | POST /api/v1/recordings/analyze
  | audio + scene manifest + simulation trace + effect catalog
  v
Backend
  1. Validate request
  2. Transcribe audio with timestamps
  3. Build candidate event windows from Unity-provided simulation trace
  4. Chapter the transcript into intent segments
  5. Align each chapter with candidate timeline events
  6. Generate effect proposals using strict JSON schema
  7. Validate generated proposals against schema + Unity catalog
  8. Return patch + chapters + confidence + warnings
  v
Unity
  |
  | Preview proposed effects on timeline
  | User accepts, rejects, or edits
```

Implementation suggestion:

- Backend: Python + FastAPI, or Node.js + Express/NestJS.
- Data validation: Pydantic if Python, Zod if TypeScript.
- AI provider wrapper: isolate OpenAI or any other model behind a service class.
- Structured model output: require JSON Schema output, then validate locally again.
- Storage: optional for v1. The main endpoint can be stateless. If debugging is needed, store analysis requests/responses by `analysisId`.

## 6. Recommended Endpoint Strategy

### 6.1 Minimal Production Surface

For Unity, start with **one main endpoint**:

```http
POST /api/v1/recordings/analyze
```

This endpoint receives the complete recording package and returns proposed timeline effects.

This is the best v1 approach because Unity does not need to coordinate multiple backend steps.

### 6.2 Useful Debug/Development Endpoints

Add optional endpoints for development, testing, and UI debugging:

```http
GET /api/v1/health
POST /api/v1/audio/transcribe
POST /api/v1/effects/propose
POST /api/v1/proposals/refine
```

The debug endpoints are useful while developing, but Unity should eventually depend mainly on `/recordings/analyze`.

## 12. Chaptering Strategy

Chaptering is useful, but it should be treated as an internal reasoning layer, not the final product.

A chapter is a short segment of intent, usually corresponding to one interaction step or one effect group.

Example:

```text
Chapter 1: ball follows hand during pinch
Chapter 2: ball stops following and jumps when hand opens
Chapter 3: hit text appears and wall changes color on collision
```

Important: a chapter is **not always exactly one effect**.

- One chapter may produce one effect.
- One chapter may produce multiple effects.
- Multiple chapters may refer to the same frame.
- One spoken sentence may contain several effects.
- One effect may require multiple pieces of evidence.

For this reason, chaptering should help the AI reason, but the final output should be timeline operations.

### Suggested Chaptering Inputs

Use both transcript and simulation events.

Transcript cues:

- `now`
- `then`
- `after that`
- `when`
- `if`
- `while`
- `until`
- `the ball follows`
- `the text appears`
- `it changes color`

Simulation cues:

- gesture starts/ends;
- collision starts/ends;
- proximity threshold crossed;
- gaze enters/exits object;
- speech command detected;
- object becomes still/moving;
- object starts/stops following another object.

### Algorithm Sketch

1. Transcribe audio with segment or word timestamps.
2. Convert transcript timestamps to frame numbers:

```text
frame = round((timeMs - audioStartMs) / 1000 * frameRate) + audioStartFrame
```

3. Build candidate event windows from simulation trace.
4. Split transcript into semantic clauses.
5. For each clause, identify:
   - candidate object mentions;
   - effect verbs;
   - temporal markers;
   - referenced gestures/collisions.
6. Align each clause to the nearest compatible event window.
7. Produce chapters.
8. Produce effect proposals from chapters.

### Critical Warning

Do not rely only on transcript timestamps. When users speak while acting, speech is often slightly before or after the corresponding action. Prefer Unity candidate events when anchoring frames.

For example:

- User says `when I pinch the ball` at frame 40.
- Pinch starts at frame 42.
- Hand-ball collision starts at frame 45.
- The `follow` effect should probably be anchored at frame 45, not frame 40.

Unity should send candidate events to reduce AI ambiguity.

Recommended candidate event types:

```text
gesture_started
gesture_ended
gesture_changed
collision_started
collision_ended
proximity_entered
proximity_exited
gaze_entered
gaze_exited
speech_command_detected
object_motion_started
object_motion_stopped
custom_marker
```

Each candidate event should include:

```json
{
  "id": "evt_123",
  "type": "collision_started",
  "frameStart": 120,
  "frameEnd": 120,
  "timeStartMs": 2000,
  "timeEndMs": 2000,
```

## 14. Effect Catalog

The backend must never invent arbitrary Unity effects.

Unity should send the effect catalog, including:

- effect type;
- valid target object types;
- required parameters;
- optional parameters;
- allowed enum values;
- default values;
- whether the effect can be automatically applied or needs review.

Recommended v1 effects:

```text
show
hide
follow
stopFollow
setColor
setText
applyImpulse
playAudio
startAnimation
stopAnimation
```

Do not include too many effects at first. A narrow catalog makes the model easier to validate.

---

## 15. Output Contract for Unity

The response should be parseable, deterministic, and safe.

Unity should be able to do this:

```text
for each operation in timelinePatch.operations:
  if operation.op == "addEffect":
    validate frame is in range
    validate target object exists
    validate effect type exists in catalog
    validate params match schema
    place proposed effect on timeline
    mark as AI proposal
    show confidence/review state in UI
```

The backend response should never directly mutate Unity state. It should return proposals.

Recommended operation types:

```text
addEffect
updateEffect
removeEffect
moveEffect
```

For v1, `addEffect` is enough.

---

## 16. Validation Rules

After AI generation, the backend must validate every proposal before returning it.

Reject or mark as invalid if:

- target object ID does not exist;
- effect type is not in the effect catalog;
- target object type is incompatible with the effect;
- required parameters are missing;
- parameter values are invalid;
- frame is outside the recording duration;
- effect duplicates an existing default effect without a reason;
- confidence is below a configured minimum.

Default show effect at frame 0:

- Mucho may already add a default `show` effect at frame 0 for assets.
- The AI should not duplicate this default show effect.
- If the user explicitly says `show the text when the ball hits the wall`, the backend can add a new show effect for that text at the collision frame.

---

## 17. Confidence and Review Rules

Every generated effect should have:

```json
{
  "confidence": 0.0,
  "reviewRequired": true,
  "reason": "Short human-readable explanation."
}
```

Suggested thresholds:

```text
confidence >= 0.85: can be previewed as strong suggestion
0.65 <= confidence < 0.85: preview but mark review required
confidence < 0.65: do not include as operation; include as warning or unresolved intent
```

Examples of low-confidence cases:

- User says `make it do that`.
- User says `jump` but no target object is clear.
- User says `change color` but no color is specified.
- User says `when it hits` but there are multiple collisions.
- User refers to `this one` but no selected object was sent by Unity.

---

## 18. Prompting Requirements for the AI Layer

The model should receive a system instruction similar to this:

```text
You are the Mucho AI timeline assistant. Your task is to convert a designer's spoken description plus structured Unity simulation data into timeline effect proposals.

Return only valid JSON matching the provided schema.

Rules:
- Use only object IDs that exist in the scene manifest.
- Use only effect types that exist in the effect catalog.
- Prefer frames from candidate events over arbitrary transcript timestamps.
- Do not invent Unity effects, objects, gestures, or collisions.
- Do not duplicate existing default effects.
- If a parameter is ambiguous, infer only when reasonable and set reviewRequired=true.
- If an intent cannot be grounded in the scene or simulation trace, put it in warnings/unresolvedIntents instead of hallucinating an effect.
- Keep explanations short and useful for a Unity inspector UI.
```

The model should receive a compact, normalized JSON context rather than the full raw Unity trace if the trace is large.

## 20. Development Milestones

### Milestone 1: API Skeleton

- Create FastAPI or Express app.
- Implement `/health`.
- Implement request/response models.
- Implement `/recordings/analyze` with mock response.
- Add schema validation tests.

### Milestone 2: Unity-Compatible JSON Contract

- Unity sends real payload without audio first.
- Backend validates scene, simulation trace, effect catalog.
- Backend returns fake but schema-valid proposals.
- Unity parses and displays proposals on timeline.

### Milestone 3: Transcription

- Add audio upload.
- Add transcription service.
- Return transcript and segments.
- Convert transcript times to frames.

### Milestone 4: AI Effect Proposal

- Add AI provider.
- Use strict structured JSON schema.
- Generate chapters and effects.
- Validate proposals after model output.
- Return warnings for ambiguous cases.

### Milestone 5: Refinement Loop

- Let Unity send user correction.
- Backend returns update/remove/move operations.
- Keep previous proposal context.

### Milestone 6: Prepare for Future State Generation

- Add optional `interactionIntent` and `chapterGroup` fields.
- Do not generate states yet.
- Make sure proposals preserve enough information for future state merging.

## 21. Testing Scenarios

Codex should create fixtures for at least these cases.

### Scenario A: Grab and Follow

User says:

```text
When I pinch the ball, it follows my hand.
```

Simulation trace:

- right hand pinch starts;
- right hand collides with ball.

Expected:

- `follow` effect on ball at hand-ball collision frame.

### Scenario B: Release and Throw

User says:

```text
When I open my hand, the ball jumps forward.
```

Simulation trace:

- right hand open starts;
- ball has recent hand motion direction.

Expected:

- `stopFollow` effect on ball;
- `applyImpulse` effect on ball;
- impulse may require review if direction/magnitude are not explicit.

### Scenario C: Collision Feedback

User says:

```text
When the ball hits the wall, show the hit text and turn the wall red.
```

Simulation trace:

- ball-wall collision starts.

Expected:

- `show` effect on hit text at collision frame;
- `setColor(red)` on wall at collision frame.

### Scenario D: Ambiguous Object

User says:

```text
When it hits, change color.
```

Simulation trace:

- ball-wall collision;
- ball-trash collision;
- several objects can change color.

Expected:

- no confident effect, or review-required proposal;
- warning about ambiguous target/collision.

### Scenario E: Duplicate Default Show

User says:

```text
The ball is visible from the beginning.
```

Existing timeline:

- ball has default show at frame 0.

Expected:

- no duplicate show effect.

## 22. Recommended JSON Schema Shape

The final model output should be constrained to something like this:

```json
{
  "type": "object",
  "required": ["chapters", "timelinePatch", "warnings", "unresolvedIntents"],
  "properties": {
    "chapters": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["id", "summary", "frameStart", "frameEnd", "evidenceEventIds", "referencedObjectIds", "confidence"],
        "properties": {
          "id": { "type": "string" },
          "summary": { "type": "string" },
          "frameStart": { "type": "integer" },
          "frameEnd": { "type": "integer" },
          "evidenceEventIds": { "type": "array", "items": { "type": "string" } },
          "referencedObjectIds": { "type": "array", "items": { "type": "string" } },
          "confidence": { "type": "number", "minimum": 0, "maximum": 1 }
        }
      }
    },
    "timelinePatch": {
      "type": "object",
      "required": ["operations"],
      "properties": {
        "operations": {
          "type": "array",
          "items": {
            "type": "object",
            "required": ["op", "effect"],
            "properties": {
              "op": { "type": "string", "enum": ["addEffect"] },
              "effect": {
                "type": "object",
                "required": ["id", "frame", "targetObjectId", "effectType", "params", "source", "confidence", "reviewRequired", "reason"],
                "properties": {
                  "id": { "type": "string" },
                  "frame": { "type": "integer" },
                  "targetObjectId": { "type": "string" },
                  "effectType": { "type": "string" },
                  "params": { "type": "object" },
                  "source": { "type": "string", "enum": ["ai"] },
                  "chapterId": { "type": "string" },
                  "confidence": { "type": "number", "minimum": 0, "maximum": 1 },
                  "reviewRequired": { "type": "boolean" },
                  "reason": { "type": "string" }
                }
              }
            }
          }
        }
      }
    },
    "warnings": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["code", "message"],
        "properties": {
          "code": { "type": "string" },
          "message": { "type": "string" },
          "relatedOperationIds": { "type": "array", "items": { "type": "string" } }
        }
      }
    },
    "unresolvedIntents": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["text", "reason"],
        "properties": {
          "text": { "type": "string" },
          "reason": { "type": "string" }
        }
      }
    }
  }
}
```

## 23. What Unity Must Provide

The backend will be much better if Unity provides these data reliably:

1. A stable object ID for every scene object.
2. A human-readable name for every object.
3. A capability list for every object.
4. The effect catalog.
5. Frame rate and duration.
6. Candidate gesture events and gesture ranges.
7. Candidate collision events.
8. Existing timeline effects.
9. Default effects, especially default show at frame 0.
10. Selected object at recording time, if available.
11. Optional: gaze target, hand trajectories, object trajectories, proximity ranges.

Do not send only raw frame-by-frame data unless necessary. Prefer summarized ranges and candidate events. The backend can support raw traces later if needed.

## 24. Open Questions for the Mucho Team

These should be decided before implementation or during the first prototype.

1. Does Unity want proposals to be automatically applied or previewed first?
2. What is the exact internal Unity representation of an effect?
3. Are effect parameters already standardized?
4. Does every object have stable IDs independent from display names?
5. Is the audio recorded during miming or after miming?
6. Does the audio start exactly at frame 0, or can it start later?
7. Can Unity provide selected object/context during recording?
8. How are hands represented internally?
9. Does Mucho already distinguish gesture start/end ranges?
10. Which effects should be supported in v1?
11. Should proposed effects have visual confidence markers in the timeline?
12. Should users be able to correct the proposal by voice?

## 25. Opinionated Recommendations

1. Start with one endpoint: `/api/v1/recordings/analyze`.
2. Make chaptering internal but return chapters for debugging and explainability.
3. Keep state generation out of v1.
4. Use Unity candidate events as anchors; do not trust audio timestamps alone.
5. Use a narrow effect catalog for the first prototype.
6. Return timeline patches, not full timelines.
7. Always include confidence and review flags.
8. Treat AI output as suggestions, not ground truth.
9. Build a mock AI provider first.
10. Add real AI only after Unity can parse and display the mock proposals.
