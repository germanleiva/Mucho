# Mucho Iterative Timeline and State Workflow

This document supersedes the earlier implementation plan's decision to defer
state merging. The legacy `/api/v1/effects/propose` endpoint remains available,
but new Unity integration should use the stateless workflow below.

## Runtime Loop

```text
Unity records one interaction
Unity -> POST /api/v1/workflows/iterate with the complete timeline snapshot
Backend -> validated action patch
Unity -> applies actions
Unity -> resimulates physics when nextStep is apply_actions_and_resimulate
Unity -> rebuilds collisions and raw placeholders
Unity -> sends the complete updated snapshot
Backend -> repeats until no actions remain
Backend -> returns a merged, named state plan
Unity -> applies or reviews the state plan
```

Unity owns project mutation, physics, timeline data, and raw placeholder
construction. The backend owns intent interpretation, proposal validation, and
semantic state merging. No workflow state is stored on the server.

## Endpoint

```http
POST /api/v1/workflows/iterate
Content-Type: application/json
```

Important request fields:

- `workflowId`: stable identifier generated by Unity.
- `iteration`: zero-based action iteration count.
- `recording`: frame rate, duration, and audio start frame.
- `transcript`: original transcript and optional timestamped segments.
- `scene`: assets and context objects with stable IDs.
- `timeline.sequences`: complete enabled/disabled gesture, voice, collision,
  and existing-action snapshot.
- `statePlaceholders`: Unity-generated contiguous half-open ranges.
- `forceVectorCandidates`: Unity-generated physically meaningful velocities.
- `options`: confidence thresholds and maximum action iterations.

Every enabled sequence start and end must appear as a placeholder boundary,
together with frame `0` and `durationFrames`. Zero-length actions contribute
one boundary.

## Response Decisions

| `workflowStatus` | `nextStep` | Meaning |
| --- | --- | --- |
| `continue` | `apply_actions` | Apply the patch and send the updated snapshot. |
| `continue` | `apply_actions_and_resimulate` | Apply the patch, run Unity physics, then resend. |
| `completed` | `apply_state_plan` | Actions are complete; apply the final named states. |
| `needs_review` | `review` | Confidence, ambiguity, iteration limit, or invalid model output requires review. |
| `failed` | `none` | The AI provider failed. |

Only `applyForce` sets `requiresResimulation: true`. The model selects a
Unity-provided force candidate and scale; the backend derives the final vector
and never invents one.

## Models and Development

```env
OPENAI_ACTION_MODEL=gpt-5.4-nano
OPENAI_STATE_MODEL=gpt-5.4-nano
WORKFLOW_AI_PROVIDER=openai
```

Set `WORKFLOW_AI_PROVIDER=mock` for deterministic local and automated testing
without API usage.

The action model may reference only supplied scene IDs, sequence anchors, and
force candidates. The state model may only group adjacent placeholder IDs in
their original order. The backend validates both outputs before returning them
to Unity.

Action planning uses the versioned `action-v1` prompt. Its normalized model
context, grounding rules, few-shot scenarios, and opt-in live evaluation
command are documented in `action_prompt_v1.md`.
